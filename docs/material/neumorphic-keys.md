# 新拟态按键面板（Neumorphic Keys）制作教学

> 目标：用同色底加双向阴影做出软胶凸起，按下的时候把它压进同一个坑里。
> 产出文件：[`widgets/material/neumorphic-keys.html`](../../widgets/material/neumorphic-keys.html)
> 难度：入门 · 约 22 分钟

---

## 0. 先想清楚：只加一道投影为什么是塑料

```css
.key { background: #e0e5ec; box-shadow: 4px 4px 10px rgba(0, 0, 0, .2); }
```

这段代码有三个毛病。第一，只有暗投影意味着"物体浮在比它暗的表面上"，而面板和键同色，浮不起来。第二，同色底上少了亮投影，哪一侧受光就没有信息，圆角像印刷上去的。第三，阴影用带色的黑（`rgba(0, 0, 0, .2)`），压在同色底上会叠出一圈偏色的边，而不是一圈"更暗的自己"；组件里两条阴影都取自底色的同色相、只改明度。新拟态的两条约束是"底子与物体同色"和"光从一侧来"，同时满足就得一深一浅各一道。

所以真正的最小写法是这样：

```css
.key {
  box-shadow:
    var(--ox) var(--oy) var(--blur) var(--lo),
    calc(var(--ox) * -1) calc(var(--oy) * -1) var(--blur) var(--hi);
}
```

两道阴影的偏移互为相反数，模糊半径相同，只有颜色一深一浅。这个对称性是全部机关：凹陷只是给它俩加 `inset`。

---

## 1. 底色必须待在中间地带，推导过程很短

浅阴影要比底色亮、暗阴影要比底色暗，所以底色要同时离白和黑都有距离。演示里用 HSL 直接把这件事写成算术：

```js
var SAT = 27;        // 底色饱和度固定为灰调
var HI_STEP = 8;     // 浅阴影比底色亮的幅度
var LO_STEP = 13;    // 深阴影比底色暗的幅度
root.style.setProperty('--hi', hsl(h, SAT, clamp(l + HI_STEP, 0, 99)));
root.style.setProperty('--lo', hsl(h, SAT + 6, clamp(l - LO_STEP, 2, 99)));
```

两个步值不对称：同样的明度差，暗侧要拉开更多才看得出投影，所以 `LO_STEP` 比 `HI_STEP` 大。深侧饱和度加了 `+6`，让投影往冷一点偏，免得同饱和度下暗侧糊成一块没有色相的灰。

默认 `--surface` 在明度 91%、饱和度 27%，换成十六进制接近常见的 `#e0e5ec`：浅侧还剩 8 的余量，深侧剩得多，两头都看得见。

把明度滑块推到 99 再看：`clamp(l + 8, 0, 99)` 把浅阴影钉死在 99，底色也几乎到顶，两者相等，亮边消失，凸起塌成平板。拉到 8 那一端，深侧被 `clamp` 钉在 2，暗阴影和底色糊在一起，同样平。这就是新拟态唯一的硬约束：**底色两侧都要有可见余量**。深底也能做，明度 20% 附近接近 `#1a2032`，此时 `--ink` 自动翻成浅色，面板仍然成立；只是深底的暗侧余量很薄，轮廓主要靠浅侧那道亮边撑，`HI_STEP` 要更大一些。

## 2. 按下：把外阴影原地换成 inset 版

```css
.key:active {
  box-shadow:
    inset var(--ox) var(--oy) var(--blur) var(--lo),
    inset calc(var(--ox) * -1) calc(var(--oy) * -1) var(--blur) var(--hi);
}
```

偏移量、模糊、颜色全部照抄，只加 `inset`：同一光源下物体从凸出变成凹进，光影像跟着翻进坑里。这条规则里没有一处需要 JS。

时机为什么交给 `:active`？这个状态的输入本来就是按下与抬起，浏览器已经在维护它。换成 JS 加类要多走一次事件回调和一次样式重算，慢的机器上按下与形变成两个时刻；长按、拖出键外、多点触控这些边界还得自己补齐。

显示区天生是凹的，所以常态就写着 `inset` 版本。凸与凹只差四个字母：一套几何，两种状态。

---

## 3. `box-shadow` 的过渡在部分浏览器上不补间

`transition: box-shadow .16s ease` 之后，有的浏览器平滑插值，有的直接从一套跳到另一套。阴影列表要逐条对应才能插值：条数一致、类型一致。`inset` 与非 `inset` 的组合在某些实现里被判为无法配对，于是整个 `box-shadow` 跳过中间态。这个现象在 Safari 上被报告得最多，本站没有逐版本复测，所以只当成跨浏览器差异，不写成版本号规则。得留一条规避路线。

运算符键走的就是规避方案：两套阴影放进两个伪元素，各自常驻，只动 `opacity`。

```css
.key.fx { position: relative; box-shadow: none; }
.key.fx > span { position: relative; z-index: 1; }
.key.fx::before, .key.fx::after {
  content: ""; position: absolute; inset: 0; border-radius: inherit;
  pointer-events: none; transition: opacity .18s ease;
}
.key.fx::before {
  opacity: var(--up, 1);
  box-shadow:
    var(--ox) var(--oy) var(--blur) var(--lo),
    calc(var(--ox) * -1) calc(var(--oy) * -1) var(--blur) var(--hi);
}
.key.fx::after {
  opacity: var(--down, 0);
  box-shadow:
    inset var(--ox) var(--oy) calc(var(--d) * 1.2) var(--lo),
    inset calc(var(--ox) * -1) calc(var(--oy) * -1) calc(var(--d) * 1.2) var(--hi);
}
.key.fx:active { --up: 0; --down: 1; }
```

`::before` 常驻外阴影，`::after` 常驻 `inset` 阴影，`--up` / `--down` 只决定谁露出来；元素自身的 `box-shadow` 设为 `none`。

`opacity` 在所有浏览器上都补间，所以过渡一定存在。代价是每个键多两个伪元素和两次阴影绘制：十六个键的面板上看不出开销，别把它套进几百行的列表里。

> 坑：症状是写了 `transition: box-shadow` 之后按下没有中间态，阴影瞬间从外切到 `inset`。原因是常态那条不带 `inset`、`:active` 那条带，部分实现无法逐条配对，就整条跳过去。修法就是上面这段代码：两套阴影分别常驻在两个伪元素上，只过渡 `opacity`。

第二条规避是让常态阴影走 `filter: drop-shadow()`、按下走 `box-shadow`。它能走，但要多付两笔账：`drop-shadow` 按图形 alpha 轮廓生成阴影，"一深一浅两道对称"里的迎光亮边不好伪造；`filter` 还让元素自成层，配合 `overflow` 与后代定位时行为会变。我试过三种写法，只有伪元素这条不抖。面板上"数字键也改用伪元素交叉淡入"开关能把数字键也切成伪元素实现，长按同一个键直接对比。

## 4. 光源角度：一个变量驱动整板

阴影方向不该每个键各写一遍。把光源角读成极坐标再换算成偏移：

```js
var a = state.angle * Math.PI / 180;
root.style.setProperty('--ox', (-Math.cos(a) * PROJ).toFixed(2) + 'px');
root.style.setProperty('--oy', (-Math.sin(a) * PROJ).toFixed(2) + 'px');
```

`a` 表示光源所在方位：0 度在右，90 度在下，225 度在左上。取负号是因为暗投影落在背光一侧；浅阴影的偏移由 `calc(var(--ox) * -1)` 得到，正好回到迎光侧。`PROJ` 是投射单位，取 7，键高 32。拖动滑块转一圈，整板凹凸方向一起转。

---

## 5. 阴影尺寸与元素高度的比例

模糊半径约为投射距离的 1.8 倍（`--blur: PROJ * 1.8`）。系数压到 1 以下阴影边缘太硬，像描边不像投影；推到 3 以上阴影发散，键与面板失去附着感。

投射距离约等于元素高度的四分之一。显示区高度更大，它用的系数是 `.7`（`calc(var(--ox) * .7)`），比键的偏移略小，两者在同一光源下才不会打架。

扩散半径（`spread`）在这个风格里留在 0：加正值会让阴影沿边向外撑成一圈硬亮带，同色底上那圈亮带会被读成描边而不是投影。

---

## 6. 它不好，而且这部分不该省

第一个缺陷是对比度。文字、底色、阴影挤在同一个明度带里：默认参数下 `--surface` 明度 91，浅侧 99，深侧 78，彼此只差十几个点。WCAG 2.1 给正文的门槛是 4.5:1；这套配色天生把文字和底色往同一个方向拉，小号说明文字容易落在门槛附近。我没有逐组量过比值，要精确数字请自己跑检查工具。数字键加了粗还撑得住，辅助文字再往中间靠一点就危险。

第二个缺陷是没有可见边界。凸起全靠阴影，"这里能不能按"就缺一个可靠表达：阴影弱的键和阴影强的键在截图里几乎一样，用户分不清控件和装饰。低亮度屏幕、放大镜用户、色觉障碍的用户首先受害。

不要用在：以文字为主的界面、表单的错误提示与帮助文字、需要区分主次操作的场景。生产里用就得接受妥协，"无障碍模式"是这样补的：

```css
body.a11y .pad, body.a11y .disp, body.a11y .key { border-color: var(--edge); }
body.a11y .key { font-weight: 800; }
```

保留双向阴影，把常态那条 `transparent` 边框换成 `--edge` 色（宽度不变，所以不引起尺寸跳动），再把数字加粗到 `800`。`--edge` 是按底色明度算出的中间对比色，深底浅底都取得到。这个组合不好看，但键的边界从此有了独立于阴影的证据。

---

## 7. 接进真实项目

组件只需要三个变量：`--surface`（底色）、`--ox/--oy`（光源偏移）、`--blur`（投射模糊），挂在面板根节点上，键和显示区共用。常态的 `border: 1px solid transparent` 要留着，否则开启边框时会抖一格。

适合：计算器、调音台这类硬件拟物的面板，装饰性分组卡片，单一动作的开关组。不适合：正文容器、密集可滚动列表（每个元素两道阴影，绘制开销成倍增长）、需要区分主次按钮的地方。

`prefers-reduced-motion` 下把过渡时长压到 `.01s`：凹凸不是动效，按下没有过渡也还能用。

## 8. 自查清单

- [ ] 底色两侧都留了余量：明度推到顶和压到底时能亲眼看到凸起消失
- [ ] 常态与 `:active` 的阴影条数一致，只有 `inset` 不同
- [ ] 没有靠 JS 类来切换按下状态
- [ ] 需要平滑过渡的键走双伪元素 `opacity`，不赌 `box-shadow` 插值
- [ ] 阴影偏移由一个角度变量算出
- [ ] 模糊半径约为投射距离的 1.8 倍，投射距离约为元素高度的四分之一
- [ ] `spread` 为 0
- [ ] 有边框补偿，正文和小字经过对比度检查
- [ ] 深底（明度 20% 附近）与浅底都验证过
